# Markdown documentation maintenance

## When to Use

Use for splitting a long repository Markdown specification into per-entity files, reorganizing linked sections, creating a navigable index, or applying a decided open question consistently across linked spec and schema documents. This is documentation maintenance, not a database migration.

## Scope and prerequisites

1. Resolve the repository and exact source file from the conversation and live tree; inspect repo instructions and `git status` before editing. If a voice transcript gives contradictory path, filename, or count, re-transcribe the original recording or clarify **before** changing files; transcription can turn `SPEC.md` or `README.md` into unrelated words.
2. Determine the requested ownership boundary: move only entity sections/tables, or also surrounding group narrative. Preserve unrequested prose and existing changes rather than regenerating the entire spec.
3. When the user prioritizes universality over implementation simplicity, compare options against a client-independent platform contract, pluggable adapters, explicit capabilities and isolated client-specific extensions; do not keep recommending a single-client shortcut solely because it is easier. Separate extensible architecture from release scope: designing for multiple clients does not automatically require implementing them all in MVP. Distinguish the platform contract, external protocol, bridge and byte transport so accepting one does not silently approve the others.

## Incorporate decisions from open questions

1. Read the exact question, proposal, and surrounding MVP/post-MVP conventions; distinguish the accepted decision from any candidate details the user rejected. If the proposal ends in an either/or implementation or stage choice, clarify that fork before treating a general acceptance as a complete decision; its alternatives can change the schema and release scope. Search the repository for the question reference, proposed entity/field names, and access or lifecycle claims before editing.
2. Update the governing narrative, MVP scope, entity descriptions, schema stages, and index together. If a candidate MVP table or field is no longer needed, remove its definition and links rather than merely relabeling it; retain any accepted post-MVP behavior in the appropriate deferred entity. Preserve still-open neighboring proposals: accepting a shared task-chat foundation must not silently accept optional notifications or later direct/channel extensions. Keep authorization separate from operational checks such as active assignments and valid workflow transitions. When a decision requires uniqueness within a parent across several children, encode the parent key in the linking schema and enforce a parent-scoped unique key plus a composite FK back to the child; uniqueness on (child, item) alone permits the same item in another child of that parent. For accepted hierarchical limits, state which ancestor scopes apply (and what happens when an optional ancestor is absent), check every configured applicable limit together, and distinguish monetary/token budgets from concurrency caps; deferring a per-assignment budget must not silently defer an already-approved per-assignment run cap. Treat configurability, default values, and whether a cap exists at all as separate decisions: if the user removes MVP concurrency caps, move optional caps to post-MVP throughout the narrative, scope table, and linked entity docs, remove stale initial-value and slot-reservation claims, but preserve per-task single-active-run and idempotency guards.
3. If an answer settles only part of a multi-part question, incorporate the accepted part and narrow the original row to the unresolved part; do not silently accept the remaining proposal or renumber it. Distinguish required capabilities from transport choices: accepting both live-process and successor-process continuation makes both behaviors mandatory, but does not select a protocol or require two interfaces. Record the accepted capability in a partially accepted decision page, link it from the active row and decision index, and synchronize release scope, contracts, feature registry and scenarios while leaving implementation status unchanged. Preserve the original question in the decision page; keep an unchosen transport explicitly open and unverified installation support clearly labeled. When the remaining architecture proposal is accepted, promote the same decision page from partial to accepted, retain its original question and earlier accepted requirements, and update the index plus stale open-status references in prior decisions and consuming documents. Distinguish decision closure from implementation readiness: a fully accepted architecture can close the question while version compatibility and integration tests remain explicit implementation gates and implementation status stays unchanged. Keep adjacent recovery, delivery, heartbeat-timing and deployment questions open rather than claiming the selected protocol resolves them. Remove the row only when every part is represented in the spec. Parse numbered rows under the open-questions heading to confirm the intended ID remains or is gone and identify the next question; loose fixed-width substring checks can skip two-digit IDs. Keep the table contiguous when deleting its first data row: an inserted blank line ends a Markdown table before the remaining questions. When the last row closes, replace the now-empty table and its obsolete explanatory text with a short 'no open questions' note. Re-search for stale proposal markers and dead links, validate the index targets, and run `git diff --check`. Commit only on request and stage only the affected documentation.
4. In an iterative question-review conversation, after recording an accepted decision, return the next unresolved question and its proposed resolution so the user can decide without reopening the file. If the current question was only partially answered, return its remaining decision rather than advancing to the next ID. For a read-only request to propose a solution, quote the first active question exactly, inspect its linked contracts and prior decisions, then separate recommendation, alternatives and checks still needed; do not edit files until a decision is accepted. When the user asks to commit and accepts the next proposal in the same message, incorporate both accepted decisions before making the scoped commit; then verify the commit and working-tree status and present the following unresolved question. Preserve the proposal's decision points (especially an outstanding choice of limits or default) instead of collapsing them into an unconditional acceptance.

## Compare external implementations before proposing a contract

1. Pin each compared repository to an inspected commit and trace the relevant source, call sites and tests. Separate executable enforcement from prompt/skill instructions, design prose and illustrative shell snippets; an instruction to an agent is not a server-side guarantee. Label static inspection and unexecuted tests explicitly.
2. Compare equivalent mechanisms: clarification forwarding, child-task delegation, execution recovery, human reminders and graph traversal are different operations. Do not copy a retry count or traversal-depth constant into a clarification limit merely because both are described as escalation. Report what is implemented, what was not found in the inspected path, and what remains this product's proposed choice, with exact source attribution.
3. Revise the recommendation after inspecting the implementations; do not present an arbitrary initial default as externally validated. Keep existence of a limit, its value, configurability and exhaustion behavior separate so an acceptance of the routing model does not silently select a conditional numeric candidate.

## Document hierarchical delegation and escalation

1. Identify whether the accepted route follows actual task setters or current organizational managers. For setter-based routing, express both directions with a short chain: human → top agent → subordinate agents for delegation, then the reverse chain for escalation. Let each immediate setter answer before forwarding; do not substitute a current manager or skip intermediate setters to reach an administrator.
2. Distinguish historical assignment identity, reusable agent configuration and administrative authority. Preserve the recorded setter/recipient when assignments change; do not grant a top agent superadmin powers merely because it is the highest agent in the chain. Keep replacement, missing-setter and ambiguous-parent cases explicit rather than silently rerouting them.
3. Separate cycle prevention and duplicate suppression from a numeric depth cap. Check whether a candidate cap would stop a legitimate delegation chain before its root; exhaustion must not authorize the very hierarchy bypass the user prohibited. Preserve waiting and an observable reason when forwarding is refused, without automatic task failure or unapproved retries.
4. Synchronize the accepted route in narrative, API checks, clarification schema semantics, MVP scope, registry and scenarios. Narrow overlapping open questions to genuinely unresolved storage, handler, reply-propagation and lifecycle details; do not invent schema fields or close those questions just because the routing principle was accepted.

## Split large Markdown specs

1. Parse headings from one immutable snapshot of the source. For each subsection, stop at the next heading of the same **or higher** level, not merely the next entity heading: otherwise the last entity absorbs the following chapter. Assert expected section counts, unique IDs/filenames, and required table markers before writing.
2. Name each destination by the source's canonical table/entity identifier; retain the full section body, including status annotations and notes after tables. Leave a relative link at each original heading. Create one index (`README.md`) with readable name, relative link, short purpose, and stage where available; derive purposes from actual schema, not generic filler.
3. Apply source replacements from end to start using positions from the immutable snapshot, then update any introductory text made inaccurate by the move. Earlier replacements shift later offsets if processed forward.

## Verification and handoff

1. Compare every generated file to its original subsection, allowing only deliberate heading/blank-line normalization. Reconstruct or calculate the expected edited source from the original snapshot and compare exactly so that unrelated content loss is caught. Never declare success from a file count alone.
2. Parse the index programmatically; assert one row per entity, unique target, matching stage, and existing relative targets. Check source links too, then run `git diff --check` and inspect `git status`. For uncommitted prior changes, use the captured working-tree snapshot rather than `git show HEAD` as the preservation baseline.
3. Report counts and verification concisely. Commit only if requested, stage only the scoped documentation files, and read back the commit and clean/remaining status after `git commit`; do not imply a push.
4. Treat a removed executable-process requirement as a cross-document scope change: update registry IDs, MVP lists, task dependencies, input snapshots, UI/API responsibilities, schema attributes and indexes together. Split mixed MVP/deferred features rather than promoting unrelated extensions; preserve partially unanswered questions and archive superseded question text with the decision.
5. For insertions beside Markdown table headers and removal of the first question row, prefer a targeted replacement of the complete unique boundary snippet. Inspect the returned diff: a context-only V4A insertion can retain an extra header, and a deleted row can leave a blank line that terminates the table. Validate contiguous rows and column counts programmatically before reporting closure. On Windows CRLF files, a multiline replacement built with normalized LF can fail even when the visible text matches; preserve the observed line endings in the boundary snippet rather than retrying an overwrite that the read guard refused.
6. Expect Windows case-insensitive protection to treat a domain document named `agents.md` as an agent-instruction file. If its approval times out, do not retry through another tool or path; report the untouched file and remaining clarification separately.
7. When documenting an accepted execution handoff, distinguish atomic acceptance of input and a durable pending intent from later external delivery or process start. Reflect pending/applied meaning and same-process versus successor-process ownership consistently in contracts, schema, dispatcher, API and UI; a saved answer is not proof of dispatch. Preserve current-owner checks, restart discoverability and unchanged historical snapshots without silently closing adjacent transport, cancellation, timeout or adapter-capability questions.
